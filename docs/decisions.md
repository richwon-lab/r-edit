# 현재 결정 사항

이 문서는 2026-10-19(한국시간)까지 대화에서 정한 현재 방향이다. 아래에 없는 세부 필드명·라이브러리·알고리즘은 자동 확정하지 않는다.

## 프로젝트 식별 정보

- 프로그램 표시 이름은 R-edit다.
- 로컬 프로젝트·모듈·Dart 패키지 이름은 r_edit로 통일한다.
- GitHub 원격 주소는 사용자가 지정한 https://github.com/richwon-lab/r-edit.git 이다.
- 로컬 식별자 변경을 GitHub 저장소 이름 변경으로 해석하지 않는다.
- 이 문서는 현재 개발 결정이다. 기능 구현 완료를 의미하지 않는다.

## 개발과 저장소

- 새 프로젝트에서 시작한다. 여러 UI 기술을 비교한 뒤 언어는 Dart, 앱은 Flutter로 확정했다. Rust 엔진을 초기 구성에 추가하지 않는다.
- 아름다운 UI와 현대적인 개발 방식은 필수 조건이다. 구체적인 화면과 그리드 라이브러리는 실제 구현에서 검증하고 선택한다.
- Junie와 로컬에서 개발한다. 앱 안에 모든 기능을 넣는 방식 대신 책임별 독립 패키지·저장소로 개발한다.
- 엔진을 UI 없이 독립 개발·시험할 수 있어야 한다. 제품 배포에 Python 실행 환경을 필수로 넣지 않는다.
- UI 상세 설계는 실제 구현 시 다룬다. 현재 목표는 합의한 기능의 누락을 막고 데이터·기능 경계를 정하는 것이다.
- 제품명은 R-edit다. 기존 프로그램의 저장소는 개인 계정에 있어 조직 저장소 이름과 겹치지 않는다는 사용자 확인을 반영한다.
- 새 앱은 `r-edit`, 업무 흐름은 `r-edit-workflow`, 문서는 `r-edit-docs`로 구분한다. 독립 기능은 `nameplate-text-layout`, `nameplate-dxf-export`로 구분한다. 배포 식별자는 구현 시 정한다.

## 작업 파일과 저장

- 저장 단위는 작업 파일 전체다. 전체 제품에 현재 입력에 맞는 배치가 있어야 한다.
- 정상 판정은 추가 확인 없이 저장한다. 규칙을 벗어난 배치는 작업자가 결과를 확인하면 저장한다.
- 작업자 확인은 제품별 해당 배치 결과에 연결한다. 확인을 정상 판정으로 바꾸지 않고 원래 판정·사유를 보존한다.
- 문구·배치·관련 조건이 바뀌면 해당 확인을 다시 받는다. 수량·출력 순서만 바뀌면 배치와 확인을 유지한다.
- 배치 결과 없음·계산 미완료를 확인만으로 완료 처리하지 않는다. 미완료 편집의 별도 저장은 초기 범위에서 제외한다.
- 저장 요청 때 필요한 계산과 확인을 마치고 입력·적용 조건·완료 배치·확인을 함께 저장한다.
- 계산·확인·저장 실패나 취소 시 이전 저장 파일을 유지하고 화면의 편집 내용은 남긴다.
- 저장 가능 여부는 전체 제품과 현재 결과에서 판단한다. 별도 영속 상태값으로 중복 보관하지 않는다.
- 미완료 입력, 재계산 대상, 계산 작업 식별 정보와 진행 상태는 작업 파일별 메모리에서 관리한다.
- 파일을 열면 저장된 결과를 사용한다. 열기만으로 재계산하거나 이전 프로세스의 계산을 이어서 실행하지 않는다.
- 늦은 계산 결과, 변경 전 결과, 이전 세션의 결과가 현재 입력을 덮어쓰지 않게 한다.

## 문구와 배치

- 제품·영역·파일은 표시 이름, 문구, 목록 순서와 독립된 식별 정보로 연결한다.
- 텍스트 영역은 목록으로 표현한다. 본문·NO·RAT 세 개의 고정 필드로 제한하지 않는다.
- 원문 공백·대소문자·기호를 임의로 수정하지 않는다. 직접 지정한 줄을 이어 붙이면 현재 원문과 정확히 같아야 한다.
- 자동 줄바꿈과 직접 지정 줄바꿈은 영역별 입력 방식이다. 직접 지정도 크기·자폭·위치는 자동으로 맞춘다.
- 직접 지정 한 줄도 명시적인 입력 방식이다. 줄 경계가 없다고 자동 방식으로 바꾸지 않는다.
- 단발성 직접 지정은 다른 제품에 전파하거나 공용 패턴으로 자동 등록하지 않는다.
- 자동 그룹은 현재 작업 파일 안에서만 구성한다. 직접 지정 본문은 자동 그룹 선택에서 제외한다.
- 자동 문구 변경 시 영향을 받는 이전·새 그룹을 다시 확인한다. 수량은 문구 배치와 학습의 입력 조건이 아니다.
- 양립 가능한 여러 패턴은 모두 반영한다. 포함 관계 충돌은 더 구체적인 문구가 우선하며 숫자 우선순위는 도입하지 않는다.
- 영향 패턴의 수와 목록은 확인할 수 있게 한다. 다중 매칭 자체를 오류나 확인 필요로 표시하지 않는다.
- 글자 획 사이 빈 공간을 활용해 홀을 억지로 끼워 넣는 배치는 지원 방향에 넣지 않는다.
- 정상·참고·배치 없음·계산 불가·탐색 미완료를 구분하고 진단 사유를 보존한다.

## 발주와 제조

- 출고는 발주 단위다. 여러 발주의 제품을 한 파일로 묶는 기능은 초기 범위에 없다.
- 한 발주에 여러 제품·도안·작업 파일을 둘 수 있다. 보통 한 사람이 맡지만 서로 다른 파일을 나눠 병행할 수 있다.
- 솔벤·UV·시트지 인쇄는 인쇄 실행 단위로 파일을 나눈다. CNC는 통상 묶어 전달하고 실제 판재 배치는 생산에서 결정한다.
- Type3 객체 수 약 1천 개라는 사례를 자동 파일 분할 임계값으로 확정하지 않는다.
- 문구 작업 방식과 외곽 가공·마감을 구분한다. UV 문구와 CNC 외곽의 조합에 조각용 글자 커터 조건을 적용하지 않는다.
- 디자인의 기본 제작 조건을 가져오고 차이만 수정한다. 전체 공정·설비·고객·프로젝트 등록을 소량 작업의 선행 조건으로 만들지 않는다.
- 주문 수량, 파일에 포함한 제작 수량, 실제 그린 도안 수를 구분한다. 재출력이나 여러 공정 때문에 주문 수량을 늘리지 않는다.

## 보관과 공유

- 추가 서버 없이 기존 Google Drive에 파일을 저장하고 동기화를 맡긴다. 동일 파일의 실시간 공동 편집은 초기 범위에서 제외한다.
- 서로 다른 작업 파일은 독립 저장한다. 같은 파일은 저장·종료와 동기화를 마친 뒤 다른 사람이 이어서 작업한다.
- PC별 Drive 기준 폴더를 설정하고 내부 상대 경로로 실제 작업 파일을 연결한다. 이동·이름 변경으로 찾지 못하면 재연결한다.
- 공용 디자인·배치 기준·패턴은 항목별 독립 파일로 관리한다. 진행 중 작업은 적용한 실제 내용과 출처를 보존한다.
- 공용 원본 변경을 기존 작업에 자동 반영하지 않는다. 같은 공용 항목의 동시 수정은 초기 범위에서 제외한다.
- 공용 자료의 범위는 회사 공통·거래처 전용·내부 구분 전용·현재 작업을 구분한다. 프로젝트가 다르다는 이유만으로 같은 거래처의 자료를 끊지 않는다.
- 내부 파일은 UTF-8 JSON으로 시작한다. 저장 형식 버전과 계산 엔진 식별 정보는 구분한다.
- Type3 DXF 인코딩은 별도다. 기존 R2000·CP949 설정은 출발점이며 모든 한글·기호 호환이 검증된 것은 아니다.

## 과거 참고와 줄바꿈 자료

- 과거 제작 도안 참고는 실제 작업 파일을 연결한다. Type3 등에서 추가 수정될 수 있으므로 앱의 과거 배치를 최종 제작 도안으로 단정하지 않는다.
- 줄바꿈 자료는 성공적으로 전체 출력된 여러 줄 결과에서 수집한다. 한 줄 결과, 미리보기, 계산·저장만 한 결과, 실패·취소·제외 출력은 수집하지 않는다.
- 같은 작업 파일의 동일 사례 재출력이나 수량 변경은 신규 사례를 만들지 않는다. 다른 파일의 동일 사례는 읽을 때 묶되 출처를 보존한다.
- 수집은 학습 정답 승인이나 패턴 자동 등록이 아니다. 학습 대상 선별과 알고리즘은 후속 결정이다.

## 아직 구현 시 정할 것

문자 위치·줄 경계의 단위와 직렬화, 의도적 빈 문구 확인 조작, 구체적인 Dart 필드·클래스명, 배포 식별자, DXF 라이브러리와 폰트 측정 연동은 구현 단계에서 정한다.
