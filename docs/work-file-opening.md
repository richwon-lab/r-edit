# R-edit 작업 파일 열기 계약 — 설계

검토일: 2026-11-01. **문서 설계이며 파일 열기 구현/저장 스키마 확정이 아니다.**
새 타입·명령 이름은 책임을 설명하는 후보이며 공개 API로 확정하지 않는다.
최신 사용자 결정 → [현재 결정](decisions.md) → 최신 논리 설계 → 과거 시험 순으로 적용한다.
[세션 연결 구현 계약](workflow-edit-session-binding.md), [모듈 경계](module-boundaries.md),
[실패·로그 기준](failure-diagnostics-logging.md), [개발 기준](development-foundation.md)을 함께 따른다.

## 1. 무엇을 여는가

이번 계약의 대상은 **R-edit가 저장한, 다시 편집할 한 작업 파일 전체**다.
한 발주에 여러 작업 파일은 가능하나 여러 발주를 임의 통합하지 않는다.
선택 화면이나 확장자가 아니라 문서 종류·지원 형식 버전·내용 검증으로 대상을 판별한다.

| 자료 | 의미 | 이번 열기와의 관계 |
|---|---|---|
| R-edit 작업 파일 | 제품 입력·적용 내용·수량/출력 의도·현재 완료 배치·판정/사유·필요한 확인을 보존한 재개 단위 | 이번 대상. 아래 선행 계약이 빠져 있어 아직 실제로 열 수 없음 |
| 발주 자료 등 외부 입력 | 고객의 원래 항목·문구·수량 등을 읽어 제품 입력으로 전환할 자료 | 별도 가져오기. 잘못 읽은 수량을 1로 채우거나 같은 문구 행을 병합하지 않음 |
| 재사용 도안·기준·패턴 | 여러 작업이 선택해 적용하는 공용 원본 | 별도 자료 선택/적용. 기존 작업은 실제 적용 내용과 출처를 보존하며 원본 최신값을 자동 재조회하지 않음 |
| 참고 CAD·DXF·Type3 파일 | 실제 제작 과정에서 외부 수정됐을 수 있는 참고/전달 자료 | 외부 프로그램 연결 또는 향후 명시 가져오기. R-edit 작업 파일로 해석하지 않음 |

논리 설계 8장의 `도안.vnd`는 실제 위치 연결의 예다. 이를 R-edit 정식 확장자로 채택하지 않는다.
ProductDesignConfiguration.toJson()도 정식 작업 파일이 아니다. 별도 임시 확장자/중간 작업 파일을 만들지 않는다.
종류/버전 표지가 없는 구성 JSON을 발견해도 정식 문서로 추정·승격하지 않는다.

| 진행 계산·취소·미완료 입력·재계산 대상·UI 선택 | 전체 작업 편집 상태는 미구현 | 후속 실행 세션/앱. 완료 저장 자료와 분리 |
| canSave/배치 완료 플래그 | 저장할 독립 필드로 만들지 않음 | 현재 전체 제품/결과/확인에서 계산 |

**현재 registerLoadedWork(configuration:)에 전체 문서 중 구성만 뽑아 넘기면 정식 열기가 아니다.**
수량·적용 기준·저장 결과·확인을 버리거나 앱의 별도 Map에 숨겨 보관해서는 안 된다.
현행 세션에는 그 자료의 변경/무효화·일관된 관찰 경로도 없다.

추천 연결 방향은 workflow의 완료 WorkDocument 값과 후속 작업 편집 소유 경계를 먼저 정한 뒤,
OpenWorks private 항목이 전체 문서 내용을 잃지 않는 workflow 소유자를 보유하도록 확장하는 것이다.
기존 ProductDesignEditSession은 구성 변경 책임으로 재사용할 수 있지만 구성의 정본은 계속 하나여야 한다.
앱과 workflow 또는 두 세션이 별도의 mutable configuration/revision을 관리하지 않는다.
마지막 저장 WorkDocument는 과거 불변 스냅샷일 수 있으며 현재 구성 정본과 혼동하지 않는다.
문서의 결과·수량·적용 기준을 함께 갱신하는 경계가 준비되기 전에는 정식 파일 등록을 연결하지 않는다.
이번 설계에서 거대한 WorkSession이나 빈 문서 래퍼를 추가하라는 뜻은 아니다.
현행 구성의 빈 제품 목록 허용도 빈 작업 파일 저장 허용을 뜻하지 않는다. 빈 문서 정책은 별도 결정이 필요하다.

### 완료 저장과 재열기의 불변식 — 확정 요구

- 작업 파일 전체 제품에 **현재 배치 입력과 실제 내용으로 일치하는 완료 결과**가 있어야 한다.
- 정상 완료 결과는 추가 확인 없이 저장한다. 자동 기준을 벗어난 사용자 지정/참고 완료 결과도
  기존 정책에 맞는 결과별 검토 후 저장할 수 있다. 확인이 원래 판정·사유를 덮어쓰지 않는다.
- 배치 없음·계산 불가·탐색 미완료는 확인만으로 저장 가능해지지 않는다.
  원문 보존·홀 회피 등 필수 조건 위반을 확인으로 허용하는 새 정책을 만들지 않는다.
- 결과가 사용한 형상·입력·규칙·그룹 의존 내용을 대조한다. ID/해시만 같다고 현재 결과로 수락하지 않는다.
- 수량·출력 순서만 달라지면 문구 배치 및 해당 확인은 유지한다. 수량 세부 정책/기본값은 이번에 정하지 않는다.
- 열 때는 저장된 결과와 원래 환경 식별을 복원한다. 자동 계산·최신 공용값 적용·이전 계산 재개를 하지 않는다.
- 저장 형식/결과 표현을 해석할 수 있으면 과거 엔진이 설치되지 않았다는 이유만으로 재계산하지 않는다.
  현재 환경에서 재계산/정확한 렌더링이 가능한지는 별도다. 글꼴 대체로 같은 결과라고 가장하지 않는다.
- 열기의 정합성 검사는 실제 최적 배치/충돌 검사를 다시 실행하거나 문서 작성 경위를 인증하는 절차가 아니다.
- 다시 열기에는 새 OpenedWorkId·새 세션 토큰·개정 0을 발급한다. 파일의 문서 ID는 이 실행 토큰이 아니다.

## 4. 파일 위치·문서 ID·실행 ID

| 식별 | 의미/소유 범위 | 파일 복사·이름 변경·이동 |
|---|---|---|
| 접근 위치 | 앱이 지금 읽을 로컬 경로. Drive 연결은 PC별 기준 폴더+내부 상대 경로로 보관하는 기존 방향 | 이름 변경/이동 때 위치 갱신·재연결 필요. 문서를 검색해 임의 재연결하지 않음 |
| 물리 파일 비교 키 | 한 PC의 지원 파일을 같은 열린 항목으로 판단할 앱 메모리 키 | 복사/교체/볼륨 이동 등으로 달라질 수 있음. 영구 문서 ID나 클라우드 ID가 아님 |
| 문서 자체 ID | 저장 문서 안의 논리 식별 정보. 구체 필드명/발급·복사 정책은 후속 문서 계약 | 단순 OS 복사는 바이트와 문서 ID를 그대로 복사함. 경로 변경만으로 내용 ID를 바꾸지 않음 |
| OpenedWorkId / workflow 토큰 | 열기 한 번의 실행 수명 | 닫고 다시 열면 새 값. 동일 문서 ID/파일 경로도 토큰 재사용 근거가 아님 |

추천: 서로 다른 물리 파일에 같은 문서 ID가 있어도 동일 열린 작업으로 자동 합치지 않는다.
동시에 편집 가능한 복제본을 정식 분기로 취급하는지/문서 ID 충돌을 경고할지는 미정이다.
후속 '새 작업으로 복사/재주문' 명령은 새 문서 ID와 출처 보존을 검토해야 하지만 OS 복사를 열 때 자동 변경하지 않는다.
같은 볼륨의 단순 rename은 같은 파일 객체를 유지할 수 있으나 저장 시 원자 교체·Drive 재동기화 등은 객체가 달라질 수 있다.
열린 파일의 경로가 다른 객체로 바뀌었으면 기존 항목을 자동 재지정하거나 두 번째로 편집 등록하지 않고 변경 충돌을 알린다.
외부 이동 감지·자동 재연결·다른 PC의 동일 파일 판단까지 현재 OpenWorks가 보장하는 것은 아니다.

### WorkFileIdentity 생성 추천

현행 값은 비교 키/원래 접근 정보의 문자열만 검증한다. 실제 값은 **앱의 Windows 파일 접근 경계**가 만든다.

추천은 지원 로컬 파일을 연 동일 읽기 핸들에서 얻는 볼륨/파일 식별 정보의 조합을 비교 키로 쓰는 것이다.
예시 키 형식은 Windows-local/볼륨-식별/파일-식별 같은 내부 표현이며 저장 스키마/API가 아니다.
originalAccessPath에는 호출자가 선택하거나 Drive 기준 위치에서 해석한 실제 접근 표기를 보존한다.
실제 OS 조회에 필요한 절대 경로와 사용자가 넘긴 원래 상대 연결 표기는 앱 접근 문맥에서 별도로 구분한다.
문서 내용이나 키를 단순 소문자화·Unicode 정규화하지 않는다.

대안인 경로 문자열 키만으로는 대소문자 규칙·별칭·이름 변경을 정확히 연결하기 어렵다.
SDK의 FileSystemEntity.identical은 경로 두 개의 같은 객체 여부를 비교하지만
그 결과가 재사용 가능한 파일 식별 키이거나 열린 핸들의 동일성 계약은 아니다. 링크 비교도 별도 의미다.
따라서 이번 추천에서 resolveSymbolicLinks/absolute/stat 결과만으로 물리 동일성을 보장하지 않는다.
플랫폼 조회가 실패/미지원이면 임의 경로 키로 자동 대체하지 않고 지원 범위 밖으로 반환한다.
이 네이티브 조회/지원 검사는 아직 없으며 이번에 플랫폼 브리지나 패키지를 선정·구현하지 않는다.

| 경로/환경 | 첫 지원 추천과 명시적 한계 |
|---|---|
| 일반 로컬 파일 | 검증된 로컬 파일시스템(우선 NTFS)의 일반 파일, 완전한 드라이브 절대경로. 파일 식별 조회와 읽기를 실제 시험한 조합만 지원 |
| Google Drive 동기화 로컬 폴더 | 우선 로컬에 실제 바이트가 있는 미러링 폴더. 로컬 파일과 같은 식별/읽기 검사 필요. 최신 클라우드 동기화 완료는 이 검사로 증명하지 못함 |
| Drive 스트리밍/가상 드라이브 | 별도 지원 검증 전 보류. 오프라인 표시만으로 안정적 파일 ID/Windows API 조합을 가정하지 않음. 공용 드라이브가 스트리밍만 가능할 수 있어 실제 운영 모드 확인 필요 |
| 내부 상대 연결 | 설정된 해당 PC Drive 기준 폴더를 명시해 해석. 기준 없음·루트 탈출·드라이브 상대형(C:folder)은 거부. 프로세스 현재 디렉터리로 추정하지 않음 |
| UNC·네트워크 공유·장치/확장 namespace | 첫 범위 보류. 원격 파일 ID/공유 동작의 별도 검증 없이 로컬과 같다고 취급하지 않음 |
| symlink·junction·특수 reparse/별칭 경로 | 첫 지원 밖으로 검출/안내. 단순 경로 정규화로 숨기지 않음. hard link 등 별도 이름도 물리 조회가 동일성을 증명한 범위만 대응하고 범용 별칭 추적은 하지 않음 |
| 대소문자 구분 디렉터리/비ASCII | OS가 연 실제 파일을 조회. 이름을 일괄 case-fold하지 않음. 별개 파일 ID는 별개 작업. 이 환경을 실기 검증하기 전 지원 완료로 표시하지 않음 |
| 경로 길이·후행 점/공백·잘못된 구성 | 값 수정으로 열지 않음. 실제 접근 API의 검증된 지원 범위 밖이면 지원 불가. 파일명/경로를 trim하지 않음 |

파일 ID는 재사용/파일 교체/동기화에 따른 변화가 가능하므로 영구 진실값으로 저장하지 않는다.
열린 항목의 물리 식별 근거와 접근 위치를 앱 파일 경계에서 유지하고 필요 시 재검사한다.
비동기 이후 정합성을 확인할 수 없으면 등록하지 않는다. 분산 잠금·동시 편집 보호의 대체물이 아니다.

## 5. 읽기에서 등록까지 — 추천 흐름

```text
요청한 소유 수명 캡처
 → 지원 경로/접근 위치 확인
 → 읽기 핸들 확보·파일 식별·이미 열린 작업 확인
 → 제한된 바이트 읽기와 읽기 전후 변경 확인
 → 엄격한 UTF-8 해석
 → JSON 문법/문서 종류/형식 버전 검사
 → 전체 업무 값·참조·입력/저장 결과/확인 정합성 검증
 → 소유 수명·취소·파일 동일성/변경·중복을 최종 재확인
 → 동기 등록/기존 항목 활성화 → 현재 소유 값으로 뷰 게시
```

읽기·검증 중에는 현재 작업/선택을 임시 교체하거나 빈 항목을 표시 정본으로 등록하지 않는다.
파일 핸들·읽기 버퍼는 성공/거부/취소/폐기 모두에서 정리한다. 장기 파일 잠금을 자동 도입하지 않는다.

### 이미 열렸거나 동시에 열리는 경우

- 실제 파일 식별로 기존 작업이 확인되면 **파일 재해석으로 기존 편집을 덮지 않고 기존 작업만 활성화**한다.
  현재 디스크가 달라 보이는 경우는 별도 외부 변경 안내이며 자동 reload하지 않는다.
- 같은 파일의 비동기 요청 두 개가 최초 확인을 통과할 수 있다. 등록 직전 다시 조회하고,
  먼저 등록한 작업이 있으면 나머지는 새 세션을 만들지 않고 기존 작업을 활성화한다.
  실패한/폐기된 요청의 버퍼와 핸들만 해제한다. 다른 파일 요청을 전역 차단하지 않는다.
- 최종 조회→등록→선택→게시 사이에는 await/외부 콜백을 두지 않는다.
  현행 registerLoadedWork의 동일 키 재등록 규약은 재사용하지만 읽기 전용 소유 조회/수명 확인 연결은 추가로 필요하다.
- 파일을 열며 문서 ID/물리 ID를 검사하는 과정의 await 뒤에도 현재 활성 화면을 반영 대상으로 사용하지 않는다.
  원래 ProviderScope/소유 명령 인스턴스를 캡처한다. owner 재생성 뒤 새 소유자에게 오래된 읽기를 전달하지 않는다.
- 소유자 폐기/명시 취소이면 정상 중단하고 등록·선택을 하지 않는다.
  예상 폐기를 인지한 뒤 stale notifier를 호출해 StateError를 만들지 않는다. 그렇다고 모든 StateError를 취소로 catch하지도 않는다.

성공 시 새 작업을 선택한다는 현행 등록 규약을 따른다. 다른 파일의 완료 순서까지 사용자 요청 순서로
자동 정렬하거나 '가장 최근 요청만 선택' 정책을 이번에 추가하지 않는다.
실패한 요청은 자신의 변경을 전혀 게시하지 않으며, 그 사이 다른 명령이 만든 최신 선택을 과거 값으로 되돌리지 않는다.

### 파일 변경 확인의 보장 수준

동일 핸들의 읽기 전후 길이/수정 정보와 최종 접근 위치의 파일 식별을 대조하는 제한적 검사를 추천한다.
변경이 관찰되거나 읽은 객체와 경로가 다른 객체를 가리키면 fileChangedDuringOpen 같은 정상 거부로 반환한다.
부분 JSON/참조 검증이 통과했다고 읽기 중 교체가 없었다고 추정하지 않는다.
크기·시각이 그대로인 변경, A→B→A, 검사 직후 변경, 다른 PC/클라우드 변경을 모두 막는 보장은 아니다.
추가 읽기 비교/감시/공유 모드 제한은 실제 요구와 Windows/Drive 시험 후 검토하며 지금 잠금/해시 체계를 확정하지 않는다.
감시가 필요해져도 이벤트는 재확인 계기이지 자동 덮어쓰기 명령이 아니다.

동일 파일 동시 편집은 지원하지 않는다. 작업자는 저장·종료·Drive 동기화 완료 후 인수인계한다.
다른 파일은 작업자별 독립 작업이며 발주 전체를 잠그지 않는다.
로컬 파일 식별/읽기 검사가 Drive 분산 잠금·충돌 방지·최신성 보증으로 확대되지 않는다.

## 6. 책임과 패키지 경계

| 책임 | 소유/전달 값 | 금지하는 혼용 |
|---|---|---|
| 파일 선택·Windows 경로/핸들·바이트 읽기·읽기 변경 확인 | 앱의 실제 파일 접근 경계. 순수 바이트·접근 결과를 다음 단계에 전달 | 위젯 또는 OpenWorks에서 JSON/업무 검증 구현 |
| 내부 형식·UTF-8/JSON·종류/버전·전체 저장 값 복원 | workflow의 후속 작업 문서 codec. OS 경로/Flutter 없이 바이트 또는 엄격 해석한 텍스트를 받는 경계 제안 | ProductDesignConfiguration JSON을 전체 파일로 간주하거나 엔진 내부 객체 그대로 저장 |
| 전체 입력/결과/확인·참조 검증 | workflow. 기존 값 생성자 및 validateProductDesignConfiguration/영역 검사를 재사용 | ID만 비교·모르는 값을 최신값/기본값으로 보정 |
| 등록·수명·선택·사용자 명령·관찰 | 앱 OpenWorks + 후속 전체 작업 소유 계약 | 원래 문서의 비구성 데이터를 앱 임의 Map에 보관해 손실 은폐 |
| 계산/출력 | 엔진/DXF 패키지의 공개 값으로 workflow가 변환 | 저장 파일 스키마를 엔진/DXF의 역방향 의존으로 전달 |

내부 파일의 UTF-8 JSON은 기존 결정이다. 읽기는 잘못된 바이트를 대체 문자로 바꾸지 않는 엄격한 UTF-8을 추천한다.
BOM 허용/거부·최대 바이트/중첩/목록 크기·알 수 없는 필드·버전 호환 표는 전체 codec 계약에서 결정한다.
UTF-16/CP949 자동 추측·잘못된 JSON 복구·임의 기본값 채우기는 하지 않는다.
저장 형식 버전과 엔진/측정 자료 식별은 독립적이며 모르는 버전을 latest로 처리하지 않는다.
CAD·Type3/DXF의 R2000·CP949/ANSI_949는 기존 별도 출력 검토 출발점이다.
내부 JSON 인코딩을 CAD 전체에 적용하거나 원문을 그 인코딩으로 변환해 저장하지 않는다.
변환 불가 문자를 '?'로 바꾸지 않으며 실제 CAD/Type3 파서는 이번 범위 밖이다.

현재 Dart SDK의 dart:io·dart:convert와 채택 Freezed/json_serializable로 읽기·변환의 기본 역할을 검토한다.
Riverpod은 소유/관찰, logging은 기존 최종 처리 경계, path_provider는 앱 데이터 위치 용도이며
파일 선택/고객 작업 파일 동일성/Drive SDK 역할을 대신하지 않는다.
새 JSON·Result·상태·파일 관리 라이브러리는 필요 근거가 없어 제안/설치하지 않는다.
네이티브 파일 식별 조회는 dart:io FileStat의 공개 필드만으로 제공되지 않는다.
SDK FileSystemEntity.identical 재사용과 Windows의 작은 네이티브 조회를 대안으로 비교했으며,
핸들 기반 비교 키가 필요한 추천안에서는 후자를 검토하되 브리지/패키지는 아직 미선정이다.
후속 선정 시 기존 Windows runner 연결과 외부 라이브러리의 실제 필요·공식 유지·라이선스·전이 의존성·
고정 SDK/Windows 지원·테스트 가능성을 비교해야 한다. 이번 문서는 새 의존성 채택 허가가 아니다.

## 7. 실패·진단·로그 계약

아래 이름은 진단 후보이며 새로운 enum/API를 구현한 것이 아니다.
모든 정상 열기 거부는 새 작업을 만들지 않고 기존 구성·세션·개정·선택을 보존한다.
독립 요청의 성공/다른 사용자 명령으로 바뀐 최신 상태를 되돌리는 롤백도 하지 않는다.

| 상황/후보 사유 | 호출자에게 필요한 구조화 정보 | 처리 |
|---|---|---|
| fileNotFound / accessDenied / readFailed | 연산 단계, 플랫폼 오류 코드, 원래 원인/스택. UI의 선택 파일 표시는 별도 접근 문맥 | 원본 수정 없이 거부. 오프라인/Drive 상태를 OS 코드 하나로 단정하지 않음 |
| unsupportedLocation / identityUnavailable | 경로 종류·지원 범위·실패 연산 | 임의 키/별칭으로 대체하지 않음 |
| invalidEncoding | 기대 UTF-8, 식별 가능한 문제 바이트 위치. 임의로 CP949라고 추측한 실제 타입 없음 | 대체 문자 복구 없이 거부 |
| malformedDocument | 파싱 단계·가능하면 바이트/문자 위치를 단위와 함께 표시 | 입력 전체/주변 원문을 상세에 복제하지 않음 |
| unsupportedDocumentKind / unsupportedFormatVersion | 실제 종류/버전과 지원 범위. 메타데이터 타입 오류는 기대/실제 타입 구분 | 구성 JSON/외부 CAD를 작업 파일로 승격하지 않음 |
| invalidWorkContents | 하위 code·실제 fieldPath·상세·관련 제품/영역 ID·0 기반 위치 | 중복 ID/참조 모호함/입력 누락 등을 구분. first/last-wins·자동 보충 없음 |
| inconsistentSavedResult / reviewWithoutCurrentResult | 입력 근거/결과/확인 연결 위치·관련 ID, 불일치한 필드 경로 | 잘못된 결과를 현재로 표시하거나 확인만으로 결과 생성하지 않음 |
| fileChangedDuringOpen | 관찰한 식별/크기/시각 변화, 확인 단계 | 자동 재읽기 무한 반복/원본 복구/덮어쓰기 없음 |
| ownerDisposed / cancelled | 원래 소유 요청의 정상 종료 사유 | 결과를 폐기하고 핸들/버퍼 정리. 새 owner에 등록하지 않음 |
| 이미 열린 파일 | 기존 작업 실행 ID | 실패가 아닌 기존 항목 활성화. 기존 편집 상태 유지 |

문법/하위 값 오류로 안전하게 해석할 수 없으면 그 단계에서 거부한다.
해석 가능한 제품·영역 참조의 독립 문제는 기존 수집 검증을 재사용한다.
정합성 해석이 불가능한 도안에서 모든 영역을 없는 것으로 오진하지 않는다.
필드 경로는 실제 문서 구조 확정 후 해당 배열/필드를 가리켜야 하며 지금 가짜 전체 JSON 경로를 확정하지 않는다.
byteOffset과 디코딩 후 문자 위치를 혼동하지 않고, 문자 오프셋 정책은 기존 미정 사항을 유지한다.

알려진 FileSystemException/문법/업무 예외만 의미를 아는 경계에서 정상 열기 실패로 변환한다.
API 오용·ArgumentError/StateError 등 결함을 일반 invalidFile/빈 구성으로 숨기지 않는다.
같은 예외는 rethrow, 변환은 원래 원인 객체·하위 진단·최초 스택을 유지하고 변환 경계 스택을 구분한다.
파서 원인 객체가 source나 경로를 포함할 수 있으므로 공개 진단/로그로 자동 펼치지 않고 수명을 제한한다.
진단은 작은 구체 상세를 사용하며 거대한 nullable 객체·임의 Map·오류 문자열 분석은 사용하지 않는다.

정상 열기 거부/취소는 자동 SEVERE가 아니다. UI용 원인 안내는 향후 지역화 리소스와 앱 처리 경계 책임이다.
예상 밖 실패는 기존 최초 최종 오류 경계에서 한 번 기록한다. 하위 단계마다 기록한 뒤 다시 던지지 않는다.
로그에는 기존 승인 필드만 명시적으로 선택하며 원문·전체 JSON·문서/Provider 상태·민감한 절대/상대 경로·
외부 메시지·문서 ID/키를 자동 덤프하지 않는다. UI에서 파일을 구분할 정보와 파일 로그 공개 정보는 별도다.
기존 로그 이벤트에 열기 이벤트가 없다고 억지로 다른 이벤트를 재사용하지 않는다. 실제 연결 시 필요한 이벤트/진단 선택만 별도 검토한다.

## 8. 선행 작업과 다음 최소 범위

현재 기능만으로 정식 파일 열기를 구현하는 것은 보류한다. 필요한 선행 순서는 다음과 같다.

1. workflow에서 **저장 결과와 현재 입력의 정합성·결과별 확인 계약**을 먼저 구체화한다.
   기존 WorkDocument/계산 입력 스냅샷/OperatorReview 제안을 출발점으로, 최초 지원 배치 조건·실제 결과 표현·
   문자열 위치 단위·필수 진단·그룹 의존성 범위·확인 연결을 결정한다. 엔진 구현이나 새 파일을 먼저 만들지 않는다.
2. 검토 후 가장 작은 구현은 해당 불변 입력 근거 값과 저장 결과/확인 연결의 순수 검증 부분이다.
   현재 DesignGeometry/TextAreaInput/제품 참조를 재사용하고, 실제 값 비교·잘못된 결과/확인 연결 진단부터 검증한다.
   필요한 규칙/제작 조건/결과 표현을 미정 Map·null·가짜 정상 결과로 채우지 않는다.
   합성 픽스처는 시험 자료로 구분하며 실제 엔진 계산/제작 성공을 주장하지 않는다.
3. 그 기반 위에서 전체 WorkDocument·수량/출력 표현·종류/버전·지원 codec·편집 소유/무효화 경계를 검토하고 구현한다.
   파일 읽기로 구성 외 자료가 사라지지 않는 전체 등록 계약을 준비한다.
4. 마지막으로 지원 Windows/Drive 경로·식별·제한 읽기·엄격 해석·정상 실패·등록 연결을 최소 구현한다.
   실제 파일 선택 UI·저장·동기화·CAD 파서·자동 배치 구현은 별도다.

**다음 한 가지 작업은 1번의 workflow 저장 결과/입력 정합성·결과별 확인 계약 설계다.**
결정 후 2번의 최소 값/검증 구현으로 이어간다. 이 문서로 여러 미정 모델 구현을 한꺼번에 승인하지 않는다.

## 9. 후속 검증 계획과 미정 사항

후속 실제 구현 시험에는 완료 저장 문서 재열기 시 결과/원문/지정 줄/수량 보존,
정상·참고 완료 결과와 결과 없는 확인의 구분, 수량만 바뀐 경우의 결과 유지,
공용 원본/과거 엔진 부재에서 저장 내용 보존을 포함한다.
모든 실제 공개 등록 관찰값과 전체 문서 보존을 비교하며 현재 구성만 같다는 것으로 성공 처리하지 않는다.

격리 파일/실제 ProviderContainer로 같은 파일 재열기·경쟁 로드·owner 폐기·다른 파일 성공 이후 한 요청 실패,
부재/권한/읽기/UTF-8/JSON/종류/버전/중복/참조 오류·읽는 중 파일 교체를 검증한다.
지원 파일시스템의 대소문자·rename·복사·Drive 로컬/오프라인 특성은 별도 Windows 실기로 확인한다.
동시 편집·Drive 동기화·전원 장애 보호 시험 완료로 확대하지 않는다.

미정: 실제 작업 문서 스키마/확장자·버전 호환·BOM/크기 제한, 완료 결과/문자 위치·엔진 정보 표현,
수량 상세, 복사 문서 ID 정책, 전체 편집 소유 확장, 파일 식별 네이티브 경계·실제 Drive 모드/지원 파일시스템이다.
이들은 구현자의 임의 선택으로 채워도 된다는 뜻이 아니다.

### 공식 자료 확인 — 2026-11-01

- [Windows 파일 ID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info):
  볼륨/파일 ID로 한 PC의 핸들이 같은 파일인지 비교하는 근거. 영구 클라우드 문서 ID가 아님.
- [핸들 정보 조회](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex):
  실제 OS/드라이버 지원 검증 필요. API 소개가 이번 앱 구현/시험을 뜻하지 않음.
- [Windows 대소문자 구분](https://learn.microsoft.com/en-us/windows/wsl/case-sensitivity): 이름의 일괄 소문자화를 피하는 근거.
- [Google Drive 스트리밍/미러링](https://support.google.com/drive/answer/13401938?hl=en):
  미러링의 로컬 보관과 스트리밍 가상 위치를 구분한다. 앱 파일 ID 안정성/동기화 완료를 보증하는 문서는 아님.
- [Dart FileStat](https://api.dart.dev/dart-io/FileStat-class.html),
  [FileSystemEntity.identical](https://api.dart.dev/dart-io/FileSystemEntity/identical.html): 공개 SDK 책임 비교.
  웹 문서는 현재 배포본이므로 고정 3.13.5의 로컬 lib/io/file_system_entity.dart도 대조했다.

이번에는 경로·참조·정책/예시의 일관성을 문서로 확인한다.
운영 코드·테스트·의존성·SDK·CI·형제 저장소는 변경하지 않으며 Dart/Flutter 전체 검증·Windows/Drive 실기는 실행하지 않는다.
